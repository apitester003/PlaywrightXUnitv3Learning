## Day 97: xUnit v3 architecture, and how it differs from v2 and NUnit

### What xUnit is

xUnit is a test framework. It finds methods marked as tests, creates objects, runs them, and reports results. It does not run browsers. Playwright does that, and your test class is the glue.

### The big change in v3: a test project is an executable

Open `PlaywrightXUnitv3Learning.csproj`:

```xml
<OutputType>Exe</OutputType>
...
<PackageReference Include="xunit.v3" Version="3.2.2" />
<PackageReference Include="xunit.runner.visualstudio" Version="3.1.5" />
```

In v2 a test project was a class library, and a separate console runner loaded it. In v3 the project is its own program (`Exe`) and contains its own runner. You can see the generated entry point in `obj/Debug/net10.0/XunitAutoGeneratedEntryPoint.cs`.

What follows from that:
- The project can be run directly as a program.
- v3 supports Microsoft.Testing.Platform (MTP), the newer test runner protocol, as well as the older VSTest path that `dotnet test` and `Microsoft.NET.Test.Sdk` use. Your project currently uses the VSTest path (see the `VSTest version` line in the output).
- The package layout changed: `xunit.v3` replaces `xunit` v2.

### v2 vs v3: the differences you will meet

| Area | v2 | v3 |
|---|---|---|
| Project type | Class library | Executable |
| Async setup and teardown | `IAsyncLifetime` returns `Task` | `IAsyncLifetime` returns `ValueTask` |
| Current test info | Not available globally | `TestContext.Current` |
| Cancellation | No token passed to tests | `TestContext.Current.CancellationToken` |
| Package | `xunit` | `xunit.v3` |

You can see the `ValueTask` change in `BaseTest.InitializeAsync`. In v2 it would return `Task`.

### xUnit vs NUnit vs MSTest

| Topic | xUnit | NUnit | MSTest |
|---|---|---|---|
| Test marker | `[Fact]`, `[Theory]` | `[Test]`, `[TestCase]` | `[TestMethod]`, `[DataRow]` |
| Per-test setup | Constructor | `[SetUp]` | `[TestInitialize]` |
| Per-test teardown | `IDisposable` / `IAsyncDisposable` | `[TearDown]` | `[TestCleanup]` |
| Instance per test | New class instance for every test | One instance per class (by default) | New instance per test |
| Shared state | Fixtures (Week 19) | Fields and `[OneTimeSetUp]` | `[ClassInitialize]` |

The most important design idea is in the "Instance per test" row. xUnit creates a new object of your test class for every single test method. That is deliberate: tests cannot leak state to each other through fields. It is also why xUnit has no `[SetUp]` attribute; the constructor does that job. Week 19 covers this in depth.

### Where this lands in this repo

`LoginTests` and `BaseTest` use `IAsyncLifetime`, which is xUnit's async setup and teardown contract. xUnit calls `InitializeAsync` after the constructor and `DisposeAsync` after each test.

## Day 98: `[Fact]` and the `Assert` API

### `[Fact]`

A `[Fact]` is a test with no parameters that is always true. Rules:
- The method is `public`.
- It returns `void`, `Task` or `ValueTask`.
- It takes no parameters. (Parameters need `[Theory]`, Week 18.)

```csharp
[Fact]
public void Day98_Equality_And_Booleans()
{
    Assert.Equal(4, 2 + 2);
    Assert.NotEqual(5, 2 + 2);
    Assert.True(10 > 3);
    Assert.False(string.IsNullOrEmpty("abc"));
}
```

A test passes if it finishes without an exception. A failing `Assert` throws, which marks the test failed.

### The argument order rule

`Assert.Equal(expected, actual)`. Always the expected value first. The failure message labels them, and a swapped order gives a misleading message. This is a common interview trap and a common code review comment.

### The Assert families you will use every day

**Strings**
```csharp
Assert.Contains("Backpack", text);
Assert.StartsWith("Sauce", text);
Assert.Equal("sauce labs backpack", text, ignoreCase: true);
Assert.Matches("^Sauce.*pack$", text);
```

**Collections**
```csharp
Assert.Contains("Onesie", names);
Assert.DoesNotContain("Jacket", names);
Assert.Single(items);                       // exactly one; returns it
Assert.Single(items, i => i.Price > 10);    // exactly one match (do not use .Where() first; analyzer xUnit2031)
Assert.All(names, n => Assert.False(string.IsNullOrWhiteSpace(n)));
Assert.Equal(new[] { "A", "B" }, names);    // compares element by element
Assert.Collection(items, i => ..., i => ...); // one lambda per element, in order
```

**Null and type**
```csharp
Assert.Null(x);  Assert.NotNull(x);
Assert.IsType<string>(value);                 // exact type
Assert.IsAssignableFrom<IEnumerable<char>>(value); // type or a subtype
```

**Floating point**
```csharp
Assert.Equal(0.3, 0.1 + 0.2, precision: 10);  // never compare doubles with exact equality
Assert.InRange(7, 1, 10);
```
For money, use `decimal`, as `ShoppingCart` does.

**Exceptions**
```csharp
var ex = Assert.Throws<ArgumentOutOfRangeException>(() => cart.Add(new CartItem("Bad", -1m)));
Assert.Equal("item", ex.ParamName);

await Assert.ThrowsAsync<InvalidOperationException>(async () => { ... });
```
`Assert.Throws<T>` needs the exact type. `Assert.ThrowsAny<T>` accepts derived types too. Both return the exception so you can assert on its details.

### `TestContext.Current.CancellationToken`

In the async test we wrote:

```csharp
await Task.Delay(1, TestContext.Current.CancellationToken);
```

xUnit v3 ships an analyzer that warns when an async test calls a cancellable API without passing the test's token. The token is cancelled if the run is aborted or the test times out. Passing it lets your test stop promptly. When you call Playwright methods you will do the same where an overload accepts a token.

### One assertion or many?

A test should check one behavior. That can need several `Assert` calls. The problem is not the number of asserts but testing two behaviors in one method. When the first assert fails, xUnit stops, so you never see the later results.

## Day 99: Naming and the Arrange-Act-Assert pattern

### Arrange, Act, Assert

Every test has three parts, separated by blank lines:

```csharp
[Fact]
public void Add_SameItemTwice_MergesQuantity()
{
    var cart = new ShoppingCart();                  // Arrange: set up

    cart.Add(new CartItem("Backpack", 29.99m));     // Act: do one thing
    cart.Add(new CartItem("Backpack", 29.99m, 2));

    Assert.Single(cart.Items);                      // Assert: check the result
    Assert.Equal(3, cart.Count);
}
```

Rules that keep tests readable:
- Arrange sets up only what this test needs.
- Act is one call, or one short action. If Act is five lines, the test is doing too much.
- Assert checks the outcome. Do not put logic (loops, `if`) in a test.

### Naming

A good name says three things: what is tested, the condition, the expected result. The common pattern is `Method_Condition_ExpectedResult`:

- `Add_NewItem_IncreasesCount`
- `Remove_UnknownItem_ReturnsFalse`
- `ApplyDiscount_Over100_Throws`

When a test fails in CI, the name is often all you see. A name like `Test1` costs your team time. A good name tells you what broke without opening the file.

Pick one convention for the team and keep it. The convention matters less than the consistency.

### UI test names

Same idea, written in terms of user behavior: `Login_WithLockedOutUser_ShowsLockedOutError`. This repo's `LoginTests` already follows it.

### Common mistakes
- Testing implementation, not behavior (asserting on private details).
- Several unrelated asserts in one test.
- Shared mutable state between tests (xUnit helps here, but static fields still leak).
- Magic numbers with no explanation. Name the value, or use a clear literal.

### Exercise

1. Rename these to the convention: `Test1`, `CartWorks`, `ItFails`. Invent what each might test on `ShoppingCart`.
2. Take any test from `LoginTests` and mark the Arrange, Act and Assert parts.

**Solution notes:** (3) Empty cart returns `0m`. One item (10.00 x 3) returns `30.00m`. For mixed items, pick values whose sum you can verify by hand.

## Day 100: Running tests: `dotnet test` and your IDE

### Command line

```bash
dotnet test                                                    # everything
dotnet test --filter "FullyQualifiedName~Week17Examples"       # by class (substring)
dotnet test --filter "FullyQualifiedName~Add_NewItem"          # by method name
dotnet test --no-build                                         # skip build when nothing changed
dotnet test --logger "console;verbosity=detailed"              # show each test
```

`~` means "contains". `=` means exact match. The `FullyQualifiedName` is `Namespace.Class.Method`.

We ran this week's tests with the second line, and it printed the summary:

```
Passed!  - Failed: 0, Passed: 14, Skipped: 1, Total: 15
```

### Other filter properties

`--filter` works on `FullyQualifiedName`, `DisplayName` and `Category`-like properties. Traits (Week 20) will give you `Category=Smoke`. We cover traits then, so do not rely on `Category` filters before that.

### Running the project directly (v3)

Because the project is an executable, `dotnet run` can start the runner itself. Not verified here, so try it and confirm the output on your machine. Add `--list-tests` if your runner version supports it.

### IDE

Visual Studio: **Test > Test Explorer**. Run all, run one, or debug one (right-click > Debug). VS Code and Rider have equivalents. You can set a breakpoint inside a test and use Debug Test. This is the fastest way to understand a failing UI test, which you practised in Phase 2.

### Habits worth having
- Run one test while writing, the class before commit, everything before push.
- A failing test should fail the same way on your machine and in CI. If it does not, look at environment differences (headless, browsers installed, data).

## Day 101: Reading test results and failures

### Anatomy of a failure

Remove `Skip` from `Day101_DeliberateFailure` and run it. I did not capture the output here, so run it and read yours. A failed `Assert.Equal` shows:
- the test name,
- the `Expected` and `Actual` values,
- the stack trace, with the line of the assert in your test.

How to read it:
1. Find the test name and the first line of your own code in the stack trace.
2. Compare Expected with Actual. Ask: is the test wrong or the code wrong?
3. Check the assert order. If expected and actual are swapped, the message misleads you.

### Failure categories, and what to do

| What you see | Likely cause | First step |
|---|---|---|
| `Assert.Equal() Failure` | Behavior differs from expectation | Debug the Act line |
| `NullReferenceException` | Missing setup or a null return | Check Arrange, nullable warnings |
| `TimeoutException` (Playwright) | Locator wrong or page slow | Trace Viewer, Week 15 |
| Passes alone, fails in a full run | Shared state or ordering | Look for statics, shared data |
| Passes locally, fails in CI | Environment (headless, data, timing) | Compare configs, read CI logs |

### Skipped tests

```csharp
[Fact(Skip = "Day 101 exercise: ...")]
```
A skipped test is reported as skipped, not passed. Skips must have a reason, and a skip with no owner and no deadline becomes permanent. Raise these in reviews.

### Exercise

1. Un-skip `Day101_DeliberateFailure`, run it, copy the failure message and annotate each line. Then fix the test (the correct count is 1) and re-skip or delete it.
2. Swap the arguments in one `Assert.Equal` and read how the message changes.
3. Break `ShoppingCart.Total` on purpose (for example, ignore Quantity). Which tests fail? What does that pattern tell you?

**Solution notes:** (3) Any test whose expected value depends on quantity fails. Tests that use quantity 1 still pass, which is exactly why a suite needs varied inputs.

## Day 102: Review, practice and interview questions

### Mini-project: test a class end to end

Write a test class `ShoppingCartTests` for `ShoppingCart` with at least 12 tests covering:
- every public member,
- both exception paths (negative price, zero quantity) and `null`,
- merge behavior,
- discount boundaries: 0, 100, -1, 101.

Aim for names a stranger could read in a CI log.

### Review checklist
- [ ] I can explain why a v3 test project is an `Exe`.
- [ ] I know `ValueTask` replaces `Task` in `IAsyncLifetime` for v3.
- [ ] I put expected first in `Assert.Equal`.
- [ ] I use `Assert.Throws<T>` and read the returned exception.
- [ ] My test names follow one convention.
- [ ] I can run one test, one class and everything from the CLI.

### Interview questions

**Junior**
1. What is the difference between `[Fact]` and `[Theory]`? *(Fact: no parameters. Theory: parameterised, Week 18.)*
2. In `Assert.Equal(a, b)`, which is expected? *(The first.)*
3. How do you assert an exception is thrown? *(`Assert.Throws<T>`, or `ThrowsAsync<T>` for async code.)*

**Mid**
4. xUnit has no `[SetUp]`. How do you do per-test setup? *(Constructor; teardown through `IDisposable`/`IAsyncDisposable`. Async: `IAsyncLifetime`.)*
5. Why does xUnit create a new instance of the class per test? *(Isolation: no state is leaked through fields.)*
6. What is the difference between `Assert.Throws<T>` and `Assert.ThrowsAny<T>`? *(Exact type vs. type or derived.)*
7. Why avoid exact equality for doubles? *(Binary floating-point rounding; use precision or `decimal`.)*

**Senior**
8. What changed from xUnit v2 to v3 that affects how you build and run a test project? *(Executable test project, `xunit.v3` packages, `ValueTask` lifetime, `TestContext.Current`, MTP support.)*
9. How would you stop a team from writing `Test1`-style names? *(Convention in the style guide, review checks, analyzers or `.editorconfig` where possible.)*
10. A test passes alone but fails in the full run. Walk me through your diagnosis. *(Shared static or external state, ordering, parallel collections. Run with reduced parallelism to confirm, then isolate the shared resource.)*

**Principal / architect**
11. How do you decide what belongs in a unit test and what in a UI test? *(Test pyramid, Week 51: logic in fast unit tests, a thin layer of UI for flows that need a browser.)*
12. How would you measure whether your test names and structure are working? *(Time-to-diagnose failures, flake rate, review feedback. Reduce the need to open code to understand a failure.)*

### On-the-job scenarios

1. **The red build at 5 pm.** A test fails in CI that passed locally. You have 15 minutes. Say what you check, in order: the failure message, whether it fails on re-run, the environment differences, then recent commits. Write your own checklist from the table on Day 101.
2. **The review comment.** A teammate's pull request has a test with eight unrelated asserts and the name `TestCart`. Draft a polite, specific review comment that explains the problem and offers a rewrite.
3. **The skip that never came back.** You find 40 skipped tests in a suite, some two years old. Decide what policy to propose. Hint: an owner, a ticket and a review date for each skip, with a periodic clean-up.
